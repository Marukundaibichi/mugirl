# MooGirl Mod 彻底重构总纲

本文档定义 MooGirl mod 的重构原则、边界、阶段划分和验收口径。当前目标不是在旧代码上继续修补，而是在不保证旧档兼容的前提下，重新建立一个可维护、性能友好、兼容性清晰的架构。

## 绝对约束

1. 不保证旧档兼容。旧存档迁移逻辑不是设计目标，旧版兼容代码应删除或隔离归档。
2. 不改动数值。任何会改变 XML 数值、C# 常量、概率、tick 间隔、产量、伤害、装备属性、生成点数、关系变化、hediff 严重度、工作耗时、贸易库存、事件权重的修改，必须先列出差异并确认。
3. 不擅自改变前后行为。若为了修复设计缺陷必须改变玩家可见行为，先写入“行为变更提案”，说明当前行为、问题、建议行为、风险和可回退方案。
4. 不保留“备份”“不能用”“临时”“AI 生成未审查”等生产源码。需要参考的旧实现只允许移入归档文档或 Git 历史，不允许继续编译。
5. 所有代码逐行审查。每个文件重构前必须完成行级审查记录，不能只靠编译通过。
6. 所有模块都有边界。新增代码不得把业务、UI、Harmony patch、存档状态、Def 解析和性能调度混在一个类里。
7. 性能优先。每 tick 逻辑必须证明必要性；能改成事件、缓存、hash interval、tick interval 或状态机的，不保留逐 tick 扫描。
8. 兼容性显式。与 DLC、HAR、Facial Animation、Search and Destroy、VCookE、其他 hediff/body mods 的交互必须通过独立兼容层表达。
9. 注释充足且必须使用中文。重构后的代码必须在非显然逻辑、状态机、性能权衡、兼容补丁、反射访问、存档字段、行为保持原因和数值不变约束处写清楚中文注释；注释解释“为什么这样做”和“不能随意改什么”，不写空洞的逐行复述。
10. 字符串全部本地化。任何玩家可见文本、设置文本、按钮文本、FloatMenu 文本、Gizmo 文本、消息、日志诊断文本、DevMode 文本和说明文本，都不得在 C# 中硬编码中文或英文；必须使用翻译键，并在语言文件中提供对应翻译。已有硬编码字符串迁移时必须保持原显示含义，不得借本地化改变文案语义。

## 当前规模快照

基于当前仓库第一轮结构扫描：

- C# 源码：143 个有效源码文件，约 13,474 行；含 bin/obj 时共 146 个 `.cs`。
- XML/Def：主要 Def/XML 约 88 个文件，约 13,609 行；全仓库 `.xml` 共 190 个。
- 资源：约 724 个 `.png`，8 个 `.wav`，2 个 `.mp3`。
- 当前主要业务域：种族与外观、基因/能力、产奶与奶制品、束具/高级束具、牵引、骑乘、加入/事件/任务、敌对公司派系、兼容补丁。
- 当前高风险点：多个 Harmony 入口、生产项目编译备份源码、每 tick Def 查询、全图 pawn 扫描、静态状态保存 Pawn/Verb、旧档迁移逻辑混入运行逻辑、命名不一致。

## 重构目标

重构完成后的项目应满足：

- 一个清晰入口：一个 Mod 类、一个 Harmony bootstrap、一个配置对象。
- 一个统一 Def 访问层：核心 DefOf 与可选 Def 缓存分离，避免运行期散落字符串查找。
- 模块化业务域：Milk、Restraints、Roping、Mounting、Incidents、Genes、Rendering、Compat 各自独立。
- 数据驱动：XML/Def 表达数值和内容；C# 表达规则和流程，不把数值硬编码在逻辑中。
- 行为可审计：每个模块都有行为契约、输入输出、失败处理和测试清单。
- 性能可证明：每 tick 代码有预算、触发条件和回退策略。
- 兼容可隔离：兼容 patch 可独立启停，不因缺少第三方 mod 报错。
- 日志可控：开发日志与玩家日志分离，正常游玩不刷屏。
- 注释可维护：复杂代码旁有足够中文上下文，后续维护者能知道设计意图、约束和风险点。
- 文本可本地化：代码只引用翻译键，语言文件承载中文、英文或其他语言文本。

## 文档结构

- `01-current-audit.md`：当前代码与 Def 的第一轮审计结论。
- `02-target-architecture.md`：目标架构、模块边界、命名和数据流。
- `03-phased-roadmap.md`：分阶段重构路线、每阶段输入/输出/验收。
- `04-value-and-behavior-lock.md`：数值冻结、行为变更审批、回归对照。
- `05-line-review-checklist.md`：逐行审查方法和文件级检查清单。
- `06-localization-and-comments.md`：中文注释与翻译键规则。

## 推荐执行顺序

1. 阶段 0：冻结基线，生成数值/行为快照。
2. 阶段 1：清理项目结构和编译入口，但不改业务。
3. 阶段 2：建立核心基础设施，包括 Def 缓存、日志、设置、tick 调度、patch registry。
4. 阶段 3：按业务域迁移模块，先低耦合后高耦合。
5. 阶段 4：重建 Def/XML 组织与兼容层。
6. 阶段 5：逐行审查、性能验证、长档运行测试。
7. 阶段 6：删除旧架构残留，整理发布包。

## 不做的事

- 不为了旧档保留旧 Scribe 字段名。
- 不把旧类简单改名后继续使用同一套耦合结构。
- 不在同一类里同时放 Harmony patch、GameComponent、UI、业务规则和 Def 查询。
- 不以“当前能运行”为验收标准。
- 不使用未审查的自动生成代码。
